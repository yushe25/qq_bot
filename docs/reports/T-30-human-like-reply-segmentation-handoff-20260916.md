## 一、目标

避免模型把停顿写成空格后作为一条消息发出。

示例：

```text
模型原始输出：
这串代码是啥 没看懂
```

期望：

```text
第一条：这串代码是啥
第二条：没看懂
```

禁止：

```text
这串代码是啥 没看懂
```

以及只包含空格、标点或空内容的独立消息。

## 二、已确认规则

1. 中英文逗号、句号、分号、冒号继续拆成多条消息。
2. 两个中文短句之间只用了空格时，空格视为停顿并拆成两条。
3. 拆完后删除边界空格，不能把空格作为某一条消息内容。
4. 英文普通空格不能被滥用为分段，例如 `hello world` 保持一条。
5. 数字、版本号、网址、文件路径、@ 和代码片段不能被误拆。
6. 原有多条发送仍经过 SafetyPipeline、内容过滤、限流和审计。
7. 每条分段必须是非空的有效文本。

## 三、当前实现与缺口

现状：[reply_style.py](../../app/agent/reply_style.py)

- 已经按 `，,。、；：` 分段。
- 未对中文短句之间的空格做语义停顿处理。
- `_clean_segment()` 把连续空白压缩为一个空格，因此模型输出
  `这串代码是啥 没看懂` 时会作为一条消息发送。

根因：

- 系统要求 persona 不随意使用逗号，但模型有时用空格代替停顿。
- 当前清洗器只做字符过滤，没有区分“词内空格”和“句间停顿”。

## 四、分段算法

### 4.1 处理顺序

1. 保存小数点和省略号占位符。
2. 先把换行、制表符和全角空格规范为普通边界。
3. 按硬标点切分：

```text
， , 。 、 ； ：
```

4. 对没有硬标点的片段执行“停顿空格”检测。
5. 清理每条新闻本。
6. 丢掉空字符串和纯标点。
7. 限制最终条数，避免超过 `safety.maxSendsPerWake`。

### 4.2 停顿空格判定

空格只有同时满足以下条件才作为分段：

- 左右两侧都有非空文本。
- 左侧至少 2 个非空白字符。
- 右侧至少 2 个非空白字符。
- 左侧或右侧至少包含一个中文字符。
- 左右两侧不是 URL、邮箱、文件路径、版本号或代码标识符。
- 空格不是 @ 前后、英文专有名词内部或 Markdown 行内代码的一部分。
- 分段结果不超过允许条数。

推荐正则和辅助函数：

```python
_CJK_RE = re.compile(r"[\u3400-\u9fff]")
_URL_OR_CODE_RE = re.compile(r"(https?://|`|\\|/|\w+\.\w+)")
```

示例：

```text
这串代码是啥 没看懂
-> ["这串代码是啥", "没看懂"]

hello world
-> ["hello world"]

版本是 3.14 元
-> ["版本是 3.14 元"]

看下 https://example.com 这个
-> ["看下 https://example.com 这个"]

@小明 你看下 这个报错了
-> ["@小明 你看下 这个报错了"]   # @ 场景保守不拆
```

### 4.3 条数上限

`normalize_reply_segments()` 增加可选参数：

```python
def normalize_reply_segments(
    text: str,
    *,
    max_segments: int | None = None,
) -> list[str]:
    ...
```

SafetyPipeline 调用时传入：

```python
max_segments=self.config.max_sends_per_wake - already_sent_count
```

超过上限时：

- 不丢弃尾部内容。
- 将超出的尾部片段合并到最后一个允许发送的片段。
- 合并时不插入空格作替代，直接拼接有效文本。
- 写一条 debug 审计，记录分段被合并。

## 五、拟人化发送节奏

当前同一批分段会连续发送。增加可选的小延迟：

```python
min_segment_delay_ms: int = 400
max_segment_delay_ms: int = 1200
```

规则：

- 只在不同分段之间延迟，不延迟第一条。
- 每条发送前重新重新检查限流。
- 延迟不能绕过 `maxSendsPerWake`、每日上限或成员数护栏。
- 可通过配置设置为 0，恢复连续发送。

未确认项：

## 十一、已确认的延迟优化规则

### 11.1 目标响应时间

- `@`、私聊、强制唤醒：第一条回复通常 `3 到 8 秒`。
- 普通聊天：第一条回复通常 `8 到 15 秒`。
- 分段消息最后一条：在前一条基础上增加约 `1 到 3 秒`。
- 需要一次工具查询：通常 `8 到 15 秒`。
- 工具查询命中缓存：通常 `6 到 10 秒`。
- 不允许经常出现一分钟级延迟。

### 11.2 按发送人等待

会话内为每个发送人维护独立的静默计时器：

```text
紧急消息：静默 2 秒，从第一条消息起最长等 5 秒
普通消息：静默 4 秒，从第一条消息起最长等 10 秒
```

规则：

- 同一发送人继续发消息，只刷新他自己的静默计时。
- 其他发送人的消息不刷新原发送人的计时。
- 其他发送人的消息仍需进入同一轮上下文。
- 多个发送人几乎同时到期时合并为一轮回复。
- 到达最长等待时间后立即处理，不能继续无限等待。
- 一批达到 20 条时立即处理。

### 11.3 冷却策略

- `@`、私聊和强制唤醒绕过冷却。
- 普通聊天继续遵守现有 90 秒冷却。
- 绕过冷却仍受发送频率和每日上限约束。

### 11.4 模型思考策略

- 普通聊天首次调用使用 `reasoning_effort=none`。
- 工具调用后的综合默认使用 `reasoning_effort=none`，避免上游要求回传不可得的推理内容。
- 不允许默认使用高推理强度处理日常闲聊。
- 具体强度通过配置控制，不写死在业务逻辑。

### 11.5 模型超时

- 单次聊天模型请求最多等 20 秒。
- 同一 Provider 不做第二次重复请求。
- 配置了备用 Provider 时，可按现有路由规则切换一次。
- 超时后不能继续占用会话 ACTIVE 状态。

## 十二、工具查询缓存

### 12.1 群成员缓存

- 每个群缓存最近一次群成员列表。
- TTL 为 5 分钟。
- 收到成员加入、退出或群成员变化事件时立即失效。
- 用于 LLM 的 `qq_get_members` 和 SafetyPipeline 成员数护栏。
- 缓存只存在内存，不写入新表。

### 12.2 群历史缓存

- 每群缓存最近 50 条历史消息。
- TTL 为 60 秒。
- 收到新消息时增量更新，不重新拉整段。
- `qq_get_group_history` 指定 limit 小于等于缓存范围时直接返回缓存。
- 请求更早历史或过期时重新查询 NapCat。

### 12.3 并发与失败

- 同一群同一资源的并发未命中只允许一个请求去取数据。
- 其他请求等待该请求结果，避免并发打满 NapCat。
- 失败结果不缓存。
- 缓存每个群独立，不能跨白名单群读取。
- 缓存按 LRU 控制数量，只保留已启用群。

### 12.4 只读工具并行

当模型同一轮同时请求：

```text
qq_get_group_history
qq_get_members
```

两个只读请求应并行执行，不能逐个等待。

```text
received_at

provider_started_at
provider_finished_at
tool_started_at / tool_finished_at
safety_started_at
first_send_at

```

输出可计算：

- 入队等待时间。
- 静默/最长等待时间。
- 模型调用耗时。
- 工具调用耗时。
- 安全检查耗时。
- 第一条和最后一条发送耗时。

埋点不得包含消息正文、Token 或密钥。
