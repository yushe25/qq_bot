# 设计契约：作息、延迟与发言节奏

- 状态：implemented
- 目标：消除 24 小时在线、固定秒回的“机器人感”。

## 目标

机器人拥有：

- 可配置的作息窗口，非活跃时段不主动发言。
- 类人的回复延迟分布，而不是固定时间。
- 随机但受控的发言节奏：单条、多条、纯表情、潜水。

## 非目标

- 不做输入法级别的逐字打字模拟。
- 不做指定用户独占回复策略。
- 不牺牲强制唤醒的安全响应。

## 触发条件

所有唤醒决策前先经过作息门禁：

- persona 活跃时段内：正常按调度器概率判断。
- 活跃时段外：私聊和 @ 仍允许响应，但延迟区间加大且不主动开话题。
- 夜间静默时段：只响应 owner 的强制唤醒，其余排队到下一个活跃窗口。
- 每日发送量达到 `safety.maxSendsPerDay` 时熔断，只写审计不发送。

## 数据契约

persona YAML 增加 `schedule`：

```yaml
schedule:
  timezone: Asia/Shanghai
  active_windows:
    - [19, 24]
    - [9, 12]
  quiet_window: [1, 8]
  reply_delay:
    min_seconds: 3
    max_seconds: 15
  mention_delay:
    min_seconds: 4
    max_seconds: 12
  sticker_only_probability: 0.15
  sticker_with_text_probability: 0.30
```

约束：

- 延迟范围必须满足 `min <= max`，单条延迟不超过 60 秒。
- 多段发言之间可按 `reply_delay` 再随机停顿。
- `sticker_only_probability + sticker_with_text_probability <= 1`。
- 作息只影响调度，不影响安全管线。

## 安全边界

- 安静时段是软边界，owner 强制唤醒和群成员 @ 不能完全被吞掉。
- 群成员 @ 或私聊通常必须响应，直接问候也算有效对话：每次唤醒可按 `scheduler.mentionDiveProbability` 小概率潜水，默认 `0.05`。
- Mention 潜水的随机判定每次唤醒只执行一次；未命中时必须先排队回复，不能通过重复调用 `qq_dive` 反复重掷。
- 发送总量熔断一旦触发，不自动恢复，需 owner 到控制台恢复。
- 作息配置缺失时使用默认窗口，不允许“永不发言”或“全天刷屏”。

## 验收指标

- 回复延迟落在配置区间内，且同一会话连续多次回复不是固定值。
- 安静时段普通消息不触发主动发言，@ 仍能在上限内响应。
- 每日发送熔断生效并写审计。
- 重启后作息配置与状态一致。
- mock 可以在不同时钟下验证活跃、安静、熔断三种状态。

## 失败与回滚

- 时钟异常或配置解析失败：退回默认窗口，不影响消息接收。
- 熔断触发后不自动清零，防止夜间刷屏。
- 配置修改热生效或重启生效由实现决定，但必须写清楚。

## 开放问题

- 是否引入随机“错过消息”概率，例如 5% 的小概率假装没看到。
- 是否允许persona在周末使用不同作息。
- 安静时段的 @ 是否允许附加冷却后的延迟上限。

## 实现记录

- 作息配置来自 `personas/*.yaml` 的 `schedule` 段，缺失或解析失败时回退默认窗口。
- 活跃窗口外：普通消息延后到下一个活跃窗口；owner/私聊/@/拍一拍可以响应，但先走随机慢响应延迟。
- Mention 唤醒会在系统提示中要求回复，收到问候时直接回问候；工具层按每次唤醒一次的随机判定决定是否允许小概率潜水；定时唤醒和普通群聊仍可正常潜水。
- 每日发送上限按本地时区日期计数，只在实际发送成功后递增；熔断后不自动恢复，控制台提供 `POST /api/sessions/{session_id}/reset-daily-sends`。
- 唤醒和发送限流同时维护全局分钟、全局小时、会话分钟与会话小时窗口；任一窗口满额都会延后到最早可用时间。
- 配置修改需要重启生效；重启后每日计数、会话状态与作息来自 SQLite 持久化。
